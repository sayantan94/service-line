Service Line Runtime
SLService Line

How the runtime works

You ask for a change and approve its plan. The engine drives two coding agents through a fixed workflow, and nothing reaches Ready without recorded evidence.

Proposed design. Not built yet.

The parts and what passes between them

One work item, step by step

Each step in detail

A skill is a short instruction file the engine hands the agent for that step. Shared skills ship with Service Line, one folder per step. A service can add its own, such as how to replay its traffic.

6ImplementImplementer

Goes in
The approved plan, one phase at a time.
Happens
  • Builds one phase, following the repository's conventions.
  • Runs the fast checks itself before handing over.
  • Updates its notes and commits a checkpoint after each phase.
  • Stops and reports if the plan no longer fits the code.

Goes in
The diff, the plan, the check results and the full service guide.
Happens

  • Walks the browser flows and replays traffic.
  • Runs scenarios the implementer never saw.
  • Reviews the diff for security and for changes nobody asked for.
  • Gives a verdict for each criterion, with evidence.

Guards against a stuck agent

GuardTriggerResult
Repeated callThe same tool call with the same arguments, several times in a rowA reminder first; at the limit the step ends
No progressThe checkout is unchanged across two roundsThe step ends
Phase capMore rounds than the plan has phases, plus a marginThe step ends
Time limitThe step's time limit expiresThe agent is stopped

A step ended by a guard goes to Needs attention and does not use up a repair.

What the search changed

  • Every step is marked agent or engine. Stripe's agents run on templates where formatting, linting and tests are fixed code and only the thinking is left to the agent. Stripe, ByteByteGo
  • Two repairs, then stop. Stripe caps its retry rounds at two for the same reason. MindStudio
  • Hidden scenarios. StrongDM keeps its test scenarios where the coding agent cannot read them, so the agent cannot build to the test. Simon Willison
  • Research before Plan, and plans in small phases. Both are common in published agent workflows. Eden AI, Playbooks
  • A fresh agent reviews. An agent reviewing its own work misses its own mistakes, which is why the plan review and Verify use the other agent. Playbooks
  • No workflow server. For one machine, saving state at each step boundary is enough; a server such as Temporal is more than this needs. Tian Pan, Developers Digest
  • Run log, recovery, sandbox, guards and the agent contract. These follow the source code of an open-source agent harness. Service Line adds a time limit per step and a hard stop for stuck agents, which that harness leaves out. DeepSeek Harness
  • Reset before retrying. Re-running an agent on a half-changed checkout gives different edits each time, so a retry starts from the last checkpoint. Engineering Playbook

Except for the harness, which was read at source level, these come from write-ups about those systems, several of them second-hand.
