Service Line

A workflow engine for software development.

The customer chooses the executor—Codex or Claude—and approves the plan. Service Line executes the work, verifies the result, and retains context and lessons locally.

It supports bug fixes, features, refactors, maintenance, and new products. AppliedIn is one Service Line instance; each requested change is a work item within it.

How it works

The instance sets an executor default; the customer can override it per work item. Agent tasks use that selection. Test and build commands run directly in the workspace.

A human reviews the scope, approach, and acceptance criteria before implementation. Approval is tied to a plan version. Scope changes require renewed approval; repairs within the approved scope follow the workflow.

Primitives

PrimitiveDefinition
InstanceOne product’s working folder, repository reference, executor defaults, work items, and local lessons. Example: AppliedIn.
Work itemOne requested outcome. Holds acceptance criteria, the versioned plan and required checks, human approval, runs, and sessions.
WorkflowA reusable ASL-style definition of planning, approval, implementation, verification, and repair. Defines transitions and limits.
ExecutorThe customer-selected coding-agent adapter: Codex or Claude. Handles agent invocation, native sessions, and results.
SessionA work item’s persistent agent conversation. Owns its executor reference, context.md, and history; can continue across runs.
RunOne execution of a workflow version for a work item. Tracks the working checkout, steps, retries, checks, outputs, and errors.

States and actions belong to the workflow. Checkouts, checks, and artifacts belong to the run. Each session belongs to one work item and one executor. Skills are reusable instructions attached to workflow tasks.

Persistent context

Each session’s context.md records decisions, progress, evidence, blockers, and next steps. Service Line loads it on continuation and checkpoints completed turns. Implementation and review use separate sessions.

Workflow progress is structured runtime state. Markdown provides agent context. Resumption checks the current workspace against the last recorded checkpoint.

Local learning

Fixes, failed attempts, and customer corrections produce candidate lessons. Validate them against checks or human review, then store them locally with their source and scope. Future planning retrieves relevant lessons. The customer can inspect, edit, or disable them.

Session context describes current work. Instance lessons inform future work. Learning cannot bypass approval or silently change an active workflow.

Add a service

Select a repository. Claude reads its README, project instructions, and test configuration to draft the description and test command. Review or edit both before creating the service. Repository inspection does not execute its commands. The customer chooses the executor for subsequent work.

Verification

Each product owns a versioned service-line-verification.md. It defines startup, fixtures, browser flows, traffic replay, assertions, and required observations. The shared verify skill follows this guide; each approved plan pins its revision and adds change-specific checks.

PartResponsibility
Check runnerRuns the approved commands on an isolated checkout. Records output, exit codes, test reports, and the exact revision.
Verification sessionUses the customer’s executor and the verify skill in a separate session. Exercises the test environment, reviews the diff and evidence, and leaves implementation files unchanged.
Workflow engineValidates evidence and decides the next state. Required checks and reviews must all pass. An agent’s completion message cannot satisfy the gate.

A failure returns to implementation for bounded repair. Missing evidence, unavailable tools, or an inconclusive review require investigation. Any code change invalidates prior verification. Scope or acceptance changes require renewed plan approval.

Browser actions, traffic replay, and observation

The guide specifies customer flows: click, type, submit, reload, and assert the visible and persisted result. Capture an action trace, screenshots at assertions, network requests and responses, and console errors.

Browser response mocking tests the frontend against controlled responses. Replaying sanitized requests against a real isolated backend tests server behavior and side effects. The contract declares which is required, its fixture/reset procedure, request ordering, and expected results.

Correlate browser and network evidence with required server logs, traces, database changes, and queue or external-service substitutes. A missing required observation is inconclusive. The guide explicitly identifies signals that do not apply.

Retain the exact code and guide revisions, environment and fixture versions, tool output, and artifact hashes with the run. The engine checks these against the approved contract before accepting a pass.

  repair_limit: 2

The instance points to the product’s verification guide. The profile is the run’s resolved check configuration from that guide and the approved plan. The run pins the guide, profile, and skill versions. The engine captures the command arguments, environment identity, exit code, output, artifact hashes, plan version, and repository snapshot—including uncommitted changes.

What the verify skill does
  1. Read the approved plan, acceptance criteria, repository instructions, diff, and runner artifacts.
  2. Check that the evidence addresses the requested behavior, including relevant failure cases. For a bug, seek a regression that fails before the fix and passes after it where reproducible.
  3. Inspect changes to tests and commands. Deleted assertions, skipped tests, or a narrower suite cannot silently weaken the approved requirements.
  4. Return passed, failed, or inconclusive for each criterion, with artifact references and actionable findings. Never invent a test result.
  5. Request additional evidence or human review when the result cannot be established. The reviewer does not edit the implementation or approve its own repair.

A separate session provides a second review; it does not guarantee correctness. The engine rejects missing artifacts, stale revisions, malformed results, unresolved required reviews, and failed mandatory checks. Human acceptance remains required for criteria assigned to a human.

Failed checks can suggest local lessons. A validated lesson can inform a future plan or test, but cannot change this run’s requirements.

Workflow contract

  • Definitions live in the Service Line repo. Each run pins a workflow version.
  • Approval is enforced by the engine. Implementation waits for a recorded human decision on the current plan.
  • Retry and repair are separate. Execution failures use Retry/Catch. Failed checks route to repair through Choice.
  • Completion requires evidence. An agent finishing a turn does not establish that the work item is correct.
  • Risk sets the depth. Each plan states a low, medium, or high risk level, approved with the plan. It decides which checks and how much human review are required. Every level keeps plan approval.
  • The line is one of four loops. A read-only observe run checks a change after a recorded deployment. A scheduled maintenance work item scans the repository and proposes work items. Learning turns past work into reviewed lessons.

Expected benefit

Less repeated context and manual coordination. Approved work proceeds through checks and bounded repairs, while local lessons improve subsequent plans. The customer focuses on scope, decisions, and results.
