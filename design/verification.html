Verification

You review evidence, not the diff. The engine decides which checks a change needs, runs them through reusable drivers, and keeps what they captured. Every correction you make becomes a check the next change has to pass.

Built: guide commands, verifier review, evidence gate, bounded repair. Designed, not built: required checks by risk, drivers, feature map, correction capture.

The verification loop

The pieces

PieceWhat it doesState
Required checksTakes the plan's risk level and the changed files and lists the checks this item must pass. Resolved at approval. A service may require more than the level asks, never less.Designed
DriversOne interface, run(flow, checkout), returning a result and artifacts. The engine runs them, not an agent, so each run is the same and costs no tokens. The drivers have their own tests.Commands built
Feature mapEvery feature under the name a user would call it: where it is, how to reach it, which flow covers it. The plan, the verifier and you share one vocabulary.Designed
FlowsSteps and assertions a driver walks: open, click, type, submit, reload, then check the visible result and the stored state.Designed
ArtifactsA screenshot per step, console and network logs, command output, all hashed and kept per attempt. A pass on a criterion must point at one.Command output built
Verifier reviewThe other agent reads the diff, the artifacts and the hidden scenarios, and gives a verdict per criterion. It cannot edit the code.Built
Evidence gatePasses only when every required check and the review passed on the current snapshot under the approved plan.Built
Capture correctionAfter a rejection, a correction or a repair, proposes a check with an error message that names the real fix. You approve it before it joins the repository.Designed

Where each piece lives

service_line/
  verification/
    guide.py          (built) also reads flows, the risk table and the feature map
    evidence.py       (built) a pass needs an artifact for every required check
    required.py       risk level + changed files -> the checks this item must pass
    featuremap.py     loads the map, picks the features a diff touches
    corrections.py    turns a rejection or failed criterion into a proposed check
    drivers/
      __init__.py     one interface: run(flow, checkout) -> result + artifacts
      command.py      shell commands (what checks.py does today)
      browser.py      headless Chrome: steps, a screenshot per step, console and network log
      replay.py       replays recorded requests and asserts the responses
  engine/actions/
    checks.py         (built) runs the required list through the drivers
    verify.py         (built) verifier gets the feature map and artifacts
    capture.py        proposes the check that would have caught the failure
  skills/verify/
    use-feature-map/  name features the way the map does
    drive-the-app/    use the driver, do not improvise
workflows/
  software-change.asl.json   + ExerciseFlows after RunChecks, + CaptureCorrection before Ready

Build order

StepWhat landsWhat it changes
1required.pyRisk decides the required checks and the gate enforces the list.
2Drivers and ExerciseFlowsThe engine walks the guide's flows and saves artifacts per attempt.
3Feature mapPlans and reviews name features the same way; the diff picks which flows run.
4capture.pyRejections and failures become proposed checks.
5Evidence view in the UIReady shows screenshots and results per criterion.

Property-based tests, model checking and state charts need no engine work. A service adds them as commands in its guide when it wants them.
